

# ESP32-S31 麦克风语音、音频播放与 AI 交互预研测试报告

##  一、摘要

本报告评估 ESP32-S31 开发板的板载麦克风、左右声道扬声器，以及本地/云端 AI 语音交互能力，重点验证音频链路质量、实时性、资源占用、功耗和产品化风险。

## 3.3 AEC回声消除算法评估

- 测试ESP32-S31在运行ACE音频调制算法所占用CPU的资源情况，对于部署AI语音识别模型进行余量分析
- 通过对比硬件和软件两种方式，在48KHz到16KHz重采样所占用的资源，来评估ESP32-S31的ASRC的硬件加速能力

### 3.3.1 软件重采样（SW_FIR）

软件路径使用 15 阶 Q15 FIR 滤波器完成 48 kHz到16 kHz、3 倍降采样。对于各个路径

输入（麦克风）RMS 为 175.6～180.2，AEC 输出 RMS 为 74.7～80.3；ERLE 为 7.00～7.47 dB。`read_err`、`write_err`、`resample_err` 与 `clip` 均为 0，表明当前 I²S、DMA、软件重采样和 AEC 数据链路连续运行正常，且未发生削波。

### 3.3.2 硬件 ASRC 加速（HW_ASRC）

硬件路径保持 ES8389 ADC/DAC 的 48 kHz、AEC 的 16 kHz、AEC 实例和测试参考信号不变，仅将 48 kHz → 16 kHz 的重采样从软件 FIR 切换为 ESP32-S31 ASRC + DMA。

首个统计窗口仍包含 AEC 自适应收敛过程（ERLE=9.47 dB）；后续稳定窗口中，AEC 音频任务 CPU 占用为 **25.24～25.32%**，重采样执行占 **0.14%**，AEC 算法执行占 **23.26～23.32%**（平均约 **7.46 ms/帧**）。ASRC 的 `wait=0.44 ms/帧` 是等待 ASRC/DMA 输出数据的时间，不应计为 CPU 忙等计算负载。

稳定窗口中输入 RMS 为 190.2～196.4，输出 RMS 为 25.5～32.6，ERLE 为 **15.59～17.46 dB**；所有 `read_err`、`write_err`、`resample_err` 与 `clip` 仍为 0。说明硬件 ASRC 路径可稳定供给 AEC 数据，且未观察到削波、丢帧或数据传输异常。

### 3.3.3 A/B 结果汇总与结论

测试条件：ES8389 采集/播放均为 48 kHz、16-bit；AEC 处理采样率固定为 16 kHz；扬声器播放 PCM 同时作为 AEC reference。除重采样实现外，软件和硬件路径的算法与接口保持一致。

| 指标 | 软件 FIR | 硬件 ASRC | 对比结论 |
| --- | ---: | ---: | --- |
| 音频任务 CPU | 27.24% | 约 25.29% | 降低约 **1.95 个百分点**（约 7.2% 相对降低） |
| 重采样执行 CPU | 4.45% | 0.14% | 降低约 **96.9%**，硬件有效卸载重采样计算 |
| AEC 执行 CPU | 23.54% | 约 23.30% | 基本不变；AEC 本体仍由 CPU 执行 |
| AEC 平均时间 | 7.532 ms/帧 | 约 7.46 ms/帧 | 基本一致 |
| ERLE（稳定窗口） | 7.00～7.47 dB | 15.59～17.46 dB | 两组均已产生回声衰减；本轮硬件路径数值更高 |
| I²S/重采样错误、削波 | 全部为 0 | 全部为 0 | 两条链路均稳定 |
| 可用内部 RAM | 409,095 B | 405,947 B | ASRC 额外使用约 3.1 KB 内部 RAM；PSRAM 相同 |

结论：

- AEC占用17%左右，为后续语音识别留有余量
- ASRC能够降低CPU重采样的负载消耗，可以有效节省CPU资源，从而更加便于部署AI模型。



- AEC 确实已参与运算：两组输出 RMS 都显著小于输入 RMS，且 ERLE 为正值；若 AEC 未工作，输出通常会接近输入、ERLE 接近 0 dB。
- 硬件 ASRC **加速的是重采样而不是 AEC 算法本体**。它将重采样 CPU 占用从 4.45% 降至 0.14%，但 AEC 仍约占 23% CPU，是当前语音链路的主要算力瓶颈。
- 在本轮测试中，启用 ASRC 后音频任务总 CPU 释放约 2 个百分点，可为唤醒词、降噪、网络传输或 UI 等并行业务留下余量，建议后续语音产品默认采用硬件 ASRC。
- 本轮 ERLE 仅可作为“回声消除链路已跑通且具备抑制效果”的证据，不能单独证明硬件 ASRC 提升了 AEC 音质。ERLE 同时受 AEC 自适应状态、扬声器音量、麦克风位置、环境反射和近端人声影响；正式横向结论需在相同音量与摆位下按 SW → HW → HW → SW 顺序各运行至少 60 秒，并丢弃前 30 秒收敛阶段后取均值和波动范围。

#### 3.4.1.1 单麦离线语音识别与高级降噪性能测试

**测试目标。** 验证 ESP32-S31 在单麦克风、16 kHz / 16-bit 采集条件下，运行 ESP-SR 离线语音识别与 NSNet2 高级降噪模型时的实时性、资源余量和识别边界。

**测试链路。**

```text
板载单麦克风 → ES8389 ADC → I²S + DMA → AFE（VAD + WakeNet9 + AGC + NSNet2）→ MultiNet7 中文命令词识别
```

其中 AFE 输入格式为 单麦格式；未开启扬声器回放、AEC、双麦 SE/波束形成、LCD 或 Wi-Fi 负载。WakeNet 模型为 `wn9_hilexin`，命令词模型为 `mn7_cn`，AFE 帧周期为 32 ms。

**结果。**

| 工况 | AFE feed 平均 / 最大耗时 | MultiNet 平均 / 最大耗时 | 系统平均空闲率 | 数据链路与资源状态 |
| --- | --- | --- | --- | --- |
| WakeNet 常驻 + NSNet2 | 6.89–6.97 ms / 7.11 ms | 未运行 | 约 84.3% | `read_err=0`；内部 RAM 约 294 KB、PSRAM 约 13.1 MB 空闲 |
| 唤醒后持续 MultiNet 识别 | 约 6.9 ms / 7.1 ms | 8.3–9.4 ms / 19.4 ms | 约 71.8%–77.2% | 无 I²S 读错；栈余量 feed/fetch 为 4948 / 4096 B，内存无持续下降 |

- NSNet2 在 AFE feed 任务中稳定运行，单帧平均耗时约 6.9 ms，占 32 ms 实时预算约 21.6%；最大值约 7.1 ms，仍保留约 24.9 ms 余量。
- MultiNet 单次推理最大约 19.4 ms，占 32 ms 命令帧预算约 60.7%，仍保留约 12.6 ms 余量。
- 在持续命令识别窗口中，AFE（含 NSNet2）约占一个核心 22%，WakeNet / MultiNet 所在核心约占 23%–34%；双核系统平均仍保留约 72% 以上空闲。

**结论：单麦问题不在 CPU 性能。**

本配置下，AFE 最大处理耗时、MultiNet 最大推理耗时均小于 32 ms 帧截止时间，且全程 `read_err=0`、内存和栈余量稳定。因此，当前距离较近、唤醒和命令词识别率不理想，不能归因于 ESP32-S31 CPU 算力不足或音频任务来不及处理。

单麦识别的主要限制是前端声学信噪比而非计算性能：

- 单麦输入没有波束形成、指向性增强和空间降噪能力；说话距离每增加一倍，语音声压约降低 6 dB，而环境噪声不会同步降低。
- NSNet2 用于抑制背景噪声，并不能恢复已被噪声淹没的远距离语音；对低能量辅音可能产生一定抑制，需通过识别率 A/B 测试验证其收益。
- AGC 可调节幅度但不能提高信噪比；ES8389 模拟 PGA 增益、麦克风方向、板卡结构遮挡、桌面反射和电源/扬声器振动都会影响输入质量。
- WakeNet 阈值和 MultiNet 命令词模型也会影响灵敏度。降低唤醒阈值可提高检出率，但会增加误唤醒，不能替代声学优化。

后续应在固定说话方向、音量和距离下，对“NS 关闭 / WebRTC NS / NSNet2”分别统计 0.3 m、0.5 m、1 m、1.5 m 的唤醒率、命令识别率与误唤醒率；若板上存在两颗独立麦克风，再开展双麦 SE/波束形成评估，作为改善中远场识别能力的主要方向。
